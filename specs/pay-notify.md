# 支付通知入口说明（我方处理）

> 依据：规划/08 BR-PAY-04 正文与细则「通知应答」、BR-PAY-05 ④、BR-PAY-08 ③（SPEC_REF `eabcf0070723fd498425b2bd1ee106da06bedae2`）；contract-delta p-29；任务 CT-21d。
> 本文件只写我方处理。渠道侧的字段名、验签算法细节与应答报文格式**待 CAP-X-16 / CAP-X-17 实测后补**，在此之前不得按臆测实现。
> 本文件是说明文档，不占契约槽、不改 `contracts/`；实现归 B2-15b～e（支付单与退款单的 CAS、20902 的返回、分录、任务入队）。

## 1. 入口路径

| 渠道 | 方法与路径 |
| --- | --- |
| 微信支付 | `POST /notify/pay/wechat` |
| 支付宝 | `POST /notify/pay/alipay` |

- 不进客户端契约（不出现在 App 用的 OpenAPI 里）。
- 不带登录态：不读、不要求任何用户或后台会话、令牌。
- 只凭验签判定来源；验签之前不信任报文里的任何字段。
- 限流。
- 不返回任何业务信息：应答只按渠道要求的格式表达「成功 / 不成功」，不回显支付单、用户、金额或错误细节。
- 20902 只用于我方的业务接口，不用于通知入口。

## 2. 验签要求

- 每条通知先验签，验签通过才进入第 3 节的核对。
- 验签失败，或应用标识、商户标识不是我方的 → 拒绝，只计数告警，不留业务痕迹（不写通知留存、不建异常收款、不迁移），不应答成功。
- 验签所需的渠道公钥 / 证书、报文中签名所在的字段与签名串的拼法：待 CAP-X-16 / CAP-X-17 实测后补。

## 3. 判定成功前的核对项（BR-PAY-04，五条，逐项）

1. 验签通过；
2. 通知（或查询结果）里的应用标识、商户标识是我方的；
3. 商户单号对应一张我方支付单；
4. 金额等于该单 `amount_fen`（用渠道返回的订单总金额对比，换算不经过浮点数）；
5. 渠道状态属于 `pay.<pay_channel>.success_states` 清单（验证前只含官方文档写明的支付成功状态，暂记微信 SUCCESS、支付宝 TRADE_SUCCESS，待实测；其余状态一律不算成功）。

任一项不符 → 不迁移，记录并告警。

核对通过后在同一事务内：PO2（PENDING → PAID，状态 CAS）、写收款分录（BR-PAY-07）、入队业务类型的开通任务（提交后执行）。同一通知重复到达、通知与查询同时到达，只生效一次。通知原文只插入留存。

支付成功只认两种来源：渠道发来并通过验签的支付通知；服务端主动查询的结果。通知与查询走同一套核对。客户端 SDK 带回的结果不作为依据。

## 4. 应答表（BR-PAY-04 细则「通知应答」逐字转写）

应答格式按各渠道的要求；20902 只用于我方的业务接口，不用于通知入口。

| 情况 | 我方处理 | 对渠道的应答 |
| --- | --- | --- |
| 核对通过，首次处理 | 同一事务内迁移、记账、入队开通 | 事务提交后应答成功 |
| 核对通过，该单已处理过（重复通知，或查询已先处理） | 不重复处理 | 应答成功 |
| 核对通过，但支付单已 CLOSED | 登记异常收款（BR-PAY-05 ④） | 登记的事务提交后应答成功 |
| 验签失败，或应用、商户标识不是我方的 | 拒绝，只计数告警，不留业务痕迹 | 不应答成功 |
| 验签通过，但商户单号找不到、金额不符或状态不在清单内 | 留存原文、告警，不迁移 | 不应答成功（渠道按它的规则重发，每次都留存；告警按单去重） |
| 处理中出错或事务失败 | 回滚 | 不应答成功 |

- CLOSED 的单不得再变为 PAID（BR-PAY-05 ④）：异常收款登记渠道、渠道交易号、商户单号、金额、证据，写异常收款分录，不触发任何业务开通，告警并生成差错单。
- 支付宝「交易完成」等清单外状态在实测进清单前按不成功处理并告警（BR-PAY-04 细则）。
